Agent Awake
WhyUsage guide

Click on. Work normally. Click off.

Use your normal Copilot or Claude chat. Green means a native request was acknowledged. Neutral @awake ready means inactive.

No extension account required

Manual power control is free and local-only: no login, API key, model request, tool call, or chat-content monitoring. It does not reroute work through a replacement participant or choose a different model.

Install the local preview

  1. Use desktop VS Code 1.95 or newer. Windows is the native-acknowledgement test target; other platforms are Unverified.
  2. Run Extensions: Install from VSIX... and choose the local preview, or launch Run Extension with F5 from the source project.
  3. Click @awake ready once. No picker or confirmation is needed.
  4. Expect the ready text to disappear and the cup to turn green; run your normal long prompt.
  5. Click the green cup again when done, or run Agent Awake: Turn Off (Allow Sleep). This never cancels native Copilot.

For explicit timed sessions, use Agent Awake: Choose Duration for a Timed Session in the Command Palette. The mode tooltip distinguishes Off, Manual, and unavailable Auto.

Supplied UI illustrations cropped to the control, not evidence of a passed hardware sleep test.

Configure hours or live-forever mode

Run Agent Awake: Configure Duration (Hours), or search Settings for @ext:apkola29.agent-keep-awake. Use 0 (the default) for until you turn it off, 0.5 for 30 minutes, or 1, 2, 4, 8 and other values up to 24 hours. The setting changes the next cup click or configured-duration command only. The one-off duration command does not change that setting. No setting activates protection by itself, and live-forever mode still ends when its window closes or reloads.

Windows keeps the screen on while enabled, requesting both system and display activity. Use AC power for long runs. The extension does not override explicit Sleep, lid/power-button actions, lock or company policy.

Opening VS Code, editing documents, changing files, running ordinary tasks, and old always/enabled settings must not start a helper or hold a power request. Hiding the indicator with agentKeepAwake.showStatusBarItem does not enable protection.

Local user acceptance checks

  • Opening VS Code starts neutral @awake ready, with no power request.
  • The control shows Starting, then a compact green cup only after protection is acknowledged.
  • Hover shows Manual mode and an explicit timed deadline or until-you-turn-it-off state.
  • Expiry and window close release the session without a persistent setting.
  • Choosing unavailable Auto from Off creates no helper or monitoring service.
  • Attempting unavailable Auto during Manual preserves the active hold and explains why.
  • Idle editor use never acquires protection.
  • Window close, reload, and crash release that window's request.
  • A manual session requests protection during ordinary chats but does not observe their completion.
  • Missing OS protection is reported as an error, never as successful protection.

Native integration tests exercise the actual power-control commands and OS requests, without model invocation. They are not evidence that native Copilot Auto or unattended sleep prevention has passed UAT.

If the cup still opens the old status message after installation, the running window has an older handler cached. Reload that window when its agent work is finished; the extension log records its loaded version.

Limits and sleep policy

Normal chat completion or its Stop button does not stop the coffee timer. Stop through the coffee icon when finished. Hiding the icon also does not stop a session. Positive durations are bounded to 24 hours; 0 has no expiry. Either mode is cleared when its window closes or reloads.

The Windows display stays on while active; power plans are not changed. macOS/Linux helper survival is not native acknowledgement, so that protection remains visibly Unverified rather than confirmed green.

Safety and privacy

Coffee mode is local-only: no model/network/authentication calls, listening server, telemetry, elevation, input simulation, or power-policy changes. The new runtime contains no chat participant, model client, hook bridge, or permission-decision logic.

The extension reads no prompts, attachments, transcripts, or provider logs. Its diagnostics report categories and counts, not private content. Off releases only this window's ownership. Security review is bounded, not a promise that all possible defects are absent.

OS policies and forced sleep/shutdown can still override a request. Linux block inhibitors may affect explicit lid/power-button suspend; native macOS/Linux validation is outstanding.

The old system-only Windows request was insufficient on this Modern Standby laptop. Native idle validation now checks actual standby/sleep events and last-input time, not just acknowledgement flags.

Local test commands

npm run typecheck
npm test
npm run test:os
npm run test:integration

The OS suite intentionally holds temporary requests. Extension integration tests use a separate profile, disable AI features, and invoke no models.

.\test\os\verify-idle-windows.ps1 -Seconds 240

This additional Windows test requires AC power and an unattended interval longer than the existing sleep/display timeout. It simulates no input and releases its own helper without changing power policy. Add -WaitForIdleSeconds 600 for a bounded wait for genuine idle. Logs include protected start/end and exact helper-release times; actual sleep events are checked before AC or input can make a run inconclusive.

Linux verification requires busctl with JSON support and a reachable logind system bus. A failed query or malformed reply fails validation; it never counts as a successfully released request.

Publication gate

The 1.2.1 candidate is for local validation; an installed VSIX is not proof of a published Marketplace update. Functional and genuine idle validation gate a public update. Native Auto is separately blocked by lifecycle/routing evidence. Nothing is automatically published.
